具体实现

1. 生产者：自动化 build.gradle.kts

遍历 nativeInterop/ohosArm64/*.def，为每个 def 注册一个 cinterop，全部打进同一个 Maven 坐标。关键点：

kotlin {
  ohosArm64 { compilations { val main by getting {
    cinterops {
      defs.forEach { d ->
        create(d.name) {
          defFile("$defDir/${d.name}.def")
          extraOpts("-Xshort-module-name", d.name)                 // ① 让 klib 有 short_name，供 depends 解析
          extraOpts("-compiler-option", "-I$hmsInclude")            // ② HMS sysroot 的扩展 Kit 头
          transitiveClosure(d.name).forEach { dep ->                // ③ 传递闭包全部 -library
            extraOpts("-library", "$cinteropDir/hilog-klib-cinterop-${dep}")
          }
        }
      }
    }
  } }
}
// ④ 任务拓扑排序：cinterop<Name 首字母大写>OhosArm64 dependsOn 闭包内各 dep
fun cinteropTaskName(name: String) = "cinterop${name.replaceFirstChar { it.uppercase() }}OhosArm64"
defs.forEach { d -> transitiveClosure(d.name).forEach { dep ->
  tasks.findByName(cinteropTaskName(d.name))?.dependsOn(cinteropTaskName(dep))
} }

publishing { publications { withType<MavenPublication> { artifactId = "hilog-klib" } } }

2. 关键工程处理

问题处理
cpf 0.4 dist 的 ohos_arm64 内置 platform klib 与我们要发的 package 同名 不清空 dist（保持原版）。cinterops 生成的 klib unique_name 不同（com.example:hilog-klib-cinterop-HiLog vs dist 的 org.jetbrains.kotlin.native.platform.HiLog），package 相同不冲突。消费者（HUAWEI，无 cpf dist 的 ohos platform lib）依赖我们的 maven klib，platform.PerformanceAnalysisKit.HiLog 从我们的 klib 解析，import 包名跟 cpf 内置一致
159 个 def 都有 enableUndefinedApiProtection=true 全部删掉。该 flag 让 cinterop stub 引用 ThrowIllegalStateExceptionFromCString，cpf 0.4 runtime 有此符号但 2.3.20-HUAWEI 没有 → 消费者 libc2k.so 加载时 relocation 失败
19 个扩展 Kit def（AIP/CANN/DeviceSecurity/HandWrite/XEngine 等）头找不到 cpf 0.4 的 additionalTargetSysRoot = sysroot-hms-aarch64-6.0.2.640-02（HMS sysroot）有这些头，但 cinterop 不自动加。全局给每个 cinterops 传 -compiler-option -I<HMS>/usr/include
cinterop 的 depends 只写直接依赖（不用写全传递） 传递依赖由各 klib manifest 链式声明。但 build 必须用 -library <dep klib path> 显式加载传递闭包：-libraryPath 只是搜索路径不自动加载；且让 cinterops 解析传递依赖到我们的 klib（unique_name com.example:...）而非 dist 内置（org.jetbrains.kotlin.native.platform.*）——消费者无 dist，depends 必须指向我们的 klib 才能解析
消费者拉 2.3.20-HUAWEI 的 KGP/stdlib settings.gradle.kts 加 devcloud 仓库（凭据放 local.properties）+ BasicAuthentication 强制认证头（devcloud 缺凭据返回 403 非 401，Gradle 默认不发认证）
cpf 0.4 的 kotlin-native-compiler-embeddable 从 Maven 解析 KGP 的 downloadKotlinNativeDistribution 从 eazytec 仓库拉 0.4.0-03 embeddable jar，无需 kotlin.native.home 指本地 dist（已去掉）

3. 消费者侧：链接 + 运行时修复

问题症状修复
KN 产出的 libc2k.so / libkn.so 无 SONAME CMake 用 IMPORTED_LOCATION 绝对路径链接后，libentry.so 的 NEEDED 记成宿主机绝对路径，设备 dlopen 失败：runHelloWorld failed: {} freeCompilerArgs += "-linker-options=-Wl,-soname,libc2k.so"，NEEDED 变成裸 soname
libkn.so NEEDED 了所有 159 个 def 的 -l 库，含设备没有的 HMS 扩展 Kit .so 设备加载 libsecurityantivirus_ndk.z.so 失败 → load module default/entry failed -linker-options=-Wl,--as-needed，只对实际引用符号的库记 NEEDED（159→15）；并加 -L<HMS>/usr/lib/aarch64-linux-ohos 让 link 阶段找得到扩展 Kit .so stub
capi demo 项目原用 0.3.0-07 + 自带 cinterop hilog 切 2.3.20-HUAWEI 后无内置 platform klib 删自己的 cinterops，ohosArm64Main { dependencies { implementation("com.example:hilog-klib:1.0-SNAPSHOT") } }；项目用到的 15 个 platform 包被 159 def 全覆盖

3a. SONAME 问题根因（待确认是否 HUAWEI 特殊）

KN 的 sharedLib 产出的 libc2k.so/libkn.so 二进制里没有 DT_SONAME 字段（readelf -d 看不到 SONAME）。在这个场景下会出问题：

  1. HarmonyOS App 的 NAPI 库 libentry.so（CMake 编译）要调用 Kotlin 代码，CMake 用 IMPORTED_LOCATION 绝对路径链接 libc2k.so
  2. 链接时 ld 看到 libc2k.so 无 SONAME，就把 IMPORTED_LOCATION 的完整绝对路径烤进 libentry.so 的 DT_NEEDED：NEEDED: /Users/.../libs/arm64-v8a/libc2k.so（正常有 SONAME 时只记裸名 libc2k.so）
  3. 设备 dlopen libentry.so → 读 NEEDED 是宿主机绝对路径 → 设备不存在 → namespace 检查失败 → load module default/entry failed → ArkTS testNapi 是 undefined → runHelloWorld failed: {}

修复：KN sharedLib 加 -linker-options=-Wl,-soname,libc2k.so，libc2k.so 有 DT_SONAME=libc2k.so，libentry.so 的 NEEDED 记裸名，设备从 App libs 目录解析。

待确认：是否 HUAWEI 版本特殊（其他 KN 版本在此场景是否也默认不设 soname），未对比。标准 KN 项目通常 libc2k.so 被 kexe 直接加载或不被别的 .so 链接，不遇到此问题；这里是"被 CMake .so 链接"的组合才暴露。

3b. publication 覆盖警告根因

KMP + maven-publish 自动创建两个 MavenPublication：

  • kotlinMultiplatform — metadata publication，含 common 的 .jar + .module（Gradle Module Metadata，记录各 target variant）
  • ohosArm64 — target publication，含 .klib + .pom

build 里 withType<MavenPublication> { artifactId = "hilog-klib" } 把两者的 artifactId 都设成 hilog-klib，于是发布时 hilog-klib-1.0-SNAPSHOT.pom 先由 kotlinMultiplatform 写一次（metadata .pom），再被 ohosArm64 覆盖写一次 → 警告 Multiple publications ... will overwrite each other!

为什么 benign：Gradle 消费者优先读 .module（含 ohosArm64 variant 坐标），按 target 选 .klib；.pom 被覆盖只影响纯 Maven 消费者（不读 .module）。我们都是 Gradle 消费者，所以之前能跑。待 #17 给两个 publication 不同 artifactId 彻底消除警告。

.so 链接策略（探索过程与最终方案）

这块绕了弯路,完整记录下来,避免重蹈覆辙。核心问题:klib 怎么让消费者 link 时找到 ohos 的 .so。 探索了 4 条路,最终落定 (c) 方案。

目标（你定的）

  • libkn.so 的 NEEDED 只含实际有调用关系的库（经过编译优化/LTO 后真正 UND 的），不是全部 159 个 —— 目的：低版本 ROM 缺库时，只缺"真正用到的"才报错，不因 NEEDED 没用的而失败
  • .so 不打进 HAP，运行时按 soname 走设备 ROM 的系统库

探索过的 4 条路

方案做法结果为什么
(a) klib 内嵌 .so,消费者解压 -L cinterops -staticLibrary 把 .so 塞进 klib 的 included/;消费者 build 解出来 -L 指向 否决 消费者要手动解压 你要求消费者零配置
(b) klib 内嵌 .so,靠 KGP 自动 -L 同 (a),但期望 KGP 自动把 included .so 加进 link 的 -L 否决 KGP 不自动 实测:KGP 对 maven 传递的 cinterops klib,创建了 included/ 目录但是空的(不解压依赖 klib 的 .so),link 命令无 -L 指向 included。KN 文档说 resources "Not used yet"。
外部 issue(socket-quic #162,2026-06)确认:maven 发布的 cinterops klib,linkerOpts 不传递,included .a 才自动 link,.so 不自动
(c) klib 只声明 linkerOpts,消费者用自己 sysroot klib manifest 带 linkerOpts=-lxxx;消费者 link 用自己 ohos sysroot(DevEco)的 .so stub;--as-needed 让 NEEDED 只含实际 UND 的;soname 让 NEEDED 记裸名 采用 已验证 消费者本就有 ohos sysroot(DevEco),(c) 方案前提是"消费者有 sysroot"
(d) 用 .a(staticLibraries) 把 .so 转 .a,用 staticLibraries 嵌入,KGP 自动 link .a 否决 cpf sysroot 只有 .so 没 .a;.a 静态链入会增大体积且不走系统运行时,违背"运行时走 ROM"

为什么 .so 不能像 .a 那样自动 link（关键发现）

  • cinterops -staticLibrary 不校验后缀:实测能嵌 .so 进 klib 的 default/targets/<target>/included/(尽管名字叫 static)。.a 和 .so 嵌入后 manifest 字段完全一样(都不新增 staticLibraries 字段)
  • 但 KGP link 时区分处理:对 maven 传递的 cinterops klib,KGP 创建了消费者 build 的 included/ 目录但留空(没解压依赖 klib 的 included .so 进去),link 命令也没有 -L 指向 included 目录
  • 外部印证:socket-quic issue #162(2026-06-13,很新)遇到完全相同问题——"maven 发布的 cinterops klib carries the bindings, not the .a; linkerOpts don't propagate to downstream consumers"。KN 社区 napperoley 也说:".so 必须在 def 定义的路径,即使消费者项目也要;要自包含只能 staticLibraries + .a"
  • 结论:KGP 当前机制下,"消费者零配置 + .so + 运行时走系统"三者不可兼得。要零配置必须 .a(但 cpf 没 .a 且不走系统);要 .so 走系统必须消费者配 -L

最终方案 (c) 的完整链路

生产者 klib (cpf 0.4 构建)
  └─ manifest: linkerOpts = -lhilog_ndk.z  // 只声明依赖,不嵌 .so

消费者 link libkn.so (2.3.20-HUAWEI)
  ├─ KN 用 HUAWEI dist 的 targetSysRoot = DevEco native/sysroot  // 主 ohos sysroot,供基础 Kit .so stub
  ├─ freeCompilerArgs += "-linker-options=-L<HMS sysroot>/usr/lib/aarch64-linux-ohos"  // 补扩展 Kit .so stub
  ├─ freeCompilerArgs += "-linker-options=-Wl,--as-needed"  // NEEDED 只含实际 UND 的库
  └─ freeCompilerArgs += "-linker-options=-Wl,-soname,libkn.so"  // NEEDED 记裸名,设备 dlopen 成功

运行时(设备)
  └─ libkn.so 的 NEEDED = [libhilog_ndk.z.so, libasset_ndk.z.so, ...实际引用的]
      └─ 设备 ROM 的 ld 按 soname 从系统库解析(基础 Kit 高版本 ROM 都有)

NEEDED 精准化的实际效果（bare 仓库 helloworld 实测）

场景NEEDED说明
无 --as-needed 159 个库全 NEEDED（含未引用的扩展 Kit） ld 要找所有 .so,DevEco sysroot 缺扩展 Kit → link 失败;即使 link 过,设备加载时缺库也失败
有 --as-needed 4 个：libc.so libhilog_ndk.z.so libasset_ndk.z.so libc++_shared.so helloworld 只用 HiLog + Asset,as-needed 按 UND 精准裁剪。低版本 ROM 只需这 4 个

注：--as-needed 不是"不查找",是"找到 .so 后判断未引用则不记 NEEDED"。所以 ld 仍要能 找到 所有 -l 声明的 .so(在 -L 路径),才能判断是否引用——这就是消费者要加 -L<HMS> 的原因（即使不用扩展 Kit）。

遗留问题与注意事项

已解决（验证通过）

  • 跨版本 ABI：cpf 0.4（abi_version 2.2.0）构建的 klib 被 2.3.20-HUAWEI（abi_version 2.3.0）读取 —— 同 major 兼容，编译/链接/运行均通过
  • 符号导出：消费者 libkn.so 的 NEEDED 含 libhilog_ndk.z.so/libasset_ndk.z.so/libhuks_ndk.z.so 等，设备进程 maps 全部加载
  • 159 def 全 cinterop 成功，0 失败
  • NEEDED 精准化：--as-needed 让 libkn.so 只 NEEDED 实际 UND 的库（bare 的 helloworld 只 NEEDED 4 个），低版本 ROM 只缺真用到的才报错
  • soname：-Wl,-soname,libkn.so 让 NEEDED 记裸名，设备 dlopen 从 App libs 目录成功
  • 运行时走系统：NEEDED 是裸 soname，设备 ROM 的 ld 按名从系统库解析，.so 不进 HAP
  • .so 链接策略落定 (c)：klib 只声明 linkerOpts，消费者用自己 ohos sysroot + 加 -L<HMS> 供扩展 Kit stub，--as-needed 精准 NEEDED。探索过自包含（嵌 .so）但 KGP 不支持，详见上文 .so 链接策略节

需注意 / 待优化

  • 消费者要装 HMS sysroot 并加 -L（(c) 方案核心 gap）：聚合 klib 带了 19 个扩展 Kit def 的 linkerOpts，--as-needed 下 ld 仍要找到这些 .so 才能判断未引用，而 DevEco 主 sysroot 没有它们。所以任何依赖聚合 hilog-klib 的消费者都要在 sharedLib 加 -linker-options=-L<HMS sysroot>/usr/lib/aarch64-linux-ohos，且本机要有这个 HMS sysroot。即使消费者代码不用扩展 Kit 也得加。consumer-bare 和 consumer-capi-demo 都加了这行。待 #14 拆分后，不用扩展 Kit 的消费者无需此 -L
  • 路径硬编码：生产者 build 的 -I<HMS include>，消费者 build 的 -L<HMS>，都是 /Users/ohoskt/... 绝对路径，换机器/CI 要改。待 #10 把 sysroot 提交进仓库后，生产者用仓库内路径；消费者只用 DevEco 路径
  • 覆盖范围：只封装了 159 个 ohos-only def。11 个共享 def（posix/linux/gles3 等）仍在 cpf 0.4 dist 内置，未进 maven klib。若消费者也缺这些，需另行封装
  • ohosX64 待支持：当前 klib 只发 ohosArm64，capi demo 的 x64 target 暂时禁用。待 #16 增加 ohosX64 支持
  • SONAME 待确认：KN sharedLib 默认不设 DT_SONAME，被 CMake 的 .so 链接时绝对路径烤进 NEEDED。当前用 -Wl,-soname 修复有效。是否 HUAWEI 版本特殊（其他 KN 版本在此场景是否也这样）未对比确认。

未做的事

  • commonTest 的 JVM 执行：capi demo 的 commonTest 跑 Android 单元测试需 ANDROID_HOME，未配置；但 ohosArm64 侧已通过 autotest.py 设备测试充分验证
  • 扩展 Kit 运行时 .so：当前 NEEDED 不含扩展 Kit（as-needed 去掉未引用）。若未来某模块真要用 securityantivirus/aip 等，设备需有对应 HMS 服务运行时（sysroot 的 .so stub 只供 link，不供运行）
  • CI 化：整套仍是本地手动跑，未写成 CI 脚本
