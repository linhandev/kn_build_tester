1. Overview — Binary Type → Export Strategy

The Kotlin/Native compiler's produce flag determines which export pipeline runs. This is set by the Gradle binary type:

Gradle binaryCompiler produceOutputExport Strategy
sharedLibDYNAMIC.so / .dylib / .dllC Export (V1 header)
staticLibSTATIC.a / .libC Export (V1 header)
frameworkFRAMEWORK.frameworkObjC Export (Apple only)
executablePROGRAMbinaryNo export
(default library)LIBRARY.klibNo binary (serialized IR)
Key insight: C export only happens for sharedLib and staticLib. Framework export uses a completely separate ObjC pipeline. A klib is not a binary — it's serialized IR that only gets C-exported when linked into a final shared/static library.

The decision is made in KonanConfig.kt:

// KonanConfig.kt line 683
internal val cInterfaceGenerationMode by lazy {
    when {
        explicitMode != null -> explicitMode
        produce == CompilerOutputKind.DYNAMIC || produce == CompilerOutputKind.STATIC
            -> CInterfaceGenerationMode.V1
        else -> CInterfaceGenerationMode.NONE
    }
}

2. The C Export Pipeline (4 Phases)

┌─────────────────────────────────────────────────────────────────────┐ │ Phase 1: Build Exports (CAdapterGenerator.kt) │ │ Walk module descriptors → collect public API elements │ │ into CAdapterExportedElements (scopes + elements tree) │ ├─────────────────────────────────────────────────────────────────────┤ │ Phase 2: Build Adapters (CAdapterCodegen.kt) │ │ For each exported element, generate LLVM bitcode bridge │ │ functions (_konan_function_N) with thread-state switching │ ├─────────────────────────────────────────────────────────────────────┤ │ Phase 3: Generate API (CAdapterApiExporter.kt) │ │ Write the .h header file + .cpp adapter file with │ │ the ExportedSymbols function-pointer struct │ ├─────────────────────────────────────────────────────────────────────┤ │ Phase 4: Compile Adapter (CAdapterCompile.kt) │ │ Compile the .cpp adapter to LLVM bitcode using │ │ clang -std=c++17 -emit-llvm, then link into final binary │ └─────────────────────────────────────────────────────────────────────┘

Phases 1–2 run during IR-to-bitcode conversion (IrToBitcode.kt). Phases 3–4 run in the backend post-processing (TopLevelPhases.kt).

3. Symbol Name Control

There are four mechanisms for controlling what C sees as symbol names. They operate at different levels and have different scopes.

3.1 Default Naming (No Annotation)

When no annotation is applied, the compiler auto-generates C names from the Kotlin fully-qualified name:

ElementC Name PatternExample
Primitive types{prefix}_KInt, {prefix}_KBoolean, etc.cexport_demo_KInt
Reference types{prefix}_kref_{package}_{Class}cexport_demo_kref_com_example_app_Animal
KType{prefix}_KTypecexport_demo_KType
NativePtr{prefix}_KNativePtrcexport_demo_KNativePtr
ExportedSymbols{prefix}_ExportedSymbolscexport_demo_ExportedSymbols
Global accessor{prefix}_symbols()cexport_demo_symbols()
Top-level functionsKotlin function name as struct memberaddNumbers
Class methodsKotlin method name as struct memberspeak, get_name
Header guardKONAN_{PREFIX}_HKONAN_CEXPORT_DEMO_H

The struct hierarchy mirrors the Kotlin package structure:

// Access pattern for a function in package com.example.app:
lib->kotlin.root.com.example.app.addNumbers(10, 32);

// Access pattern for a class method:
lib->kotlin.root.com.example.app.Animal.speak(animalRef);

// Access pattern for a top-level property:
lib->kotlin.root.com.example.app.get_appVersion();

3.2 @CName Annotation

The only public annotation for controlling C-visible symbol names. Defined in kotlin.native.Annotations.

@ExperimentalNativeApi
@Target(AnnotationTarget.FUNCTION)
@Retention(AnnotationRetention.BINARY)
annotation class CName(
    val externName: String = "",   // standalone extern "C" function
    val shortName: String = ""     // name inside ExportedSymbols struct
)

Mode A: externName only

Creates a standalone extern "C" function callable directly from C without the struct:

// Kotlin:
@CName("kn_subtract")
fun subtractNumbers(a: Int, b: Int): Int = a - b

// Generated C header includes:
RUNTIME_EXPORT extern "C" cexport_demo_KInt kn_subtract(cexport_demo_KInt a, cexport_demo_KInt b);

// C caller:
int result = kn_subtract(100, 58);  // direct call, no struct needed

Mode B: shortName only

Changes the member name inside the ExportedSymbols struct. No standalone extern "C" function:

// Kotlin:
@CName(externName = "", shortName = "myMultiply")
fun multiplyNumbers(a: Int, b: Int): Int = a * b

// No extern "C" function generated. Struct member renamed:
lib->kotlin.root.com.example.app.myMultiply(6, 7);  // "myMultiply" instead of "multiplyNumbers"

Mode C: Both externName and shortName

Creates both a standalone function and a renamed struct member:

// Kotlin:
@CName(externName = "kn_divide", shortName = "div")
fun divideNumbers(a: Double, b: Double): Double = if (b != 0.0) a / b else Double.NaN

// C caller — two ways to call:
double r1 = kn_divide(355.0, 113.0);                    // direct extern "C"
double r2 = lib->kotlin.root.com.example.app.div(355.0, 113.0);  // via struct
Constraint: @CName only applies to top-level functions. It cannot be used on class members, constructors, or classes themselves. The annotation target is AnnotationTarget.FUNCTION only.
DCE Prevention — YES, @CName does prevent Dead Code Elimination. The chain is:
@CName → in ANNOTATIONS_TO_TREAT_AS_EXPORTED (KonanMangler.kt:30)
→ isPlatformSpecificExport() returns true
→ isExported() returns true even for private top-level functions
→ FunctionSymbol.Public in DataFlowIR
→ DCE root in library mode (sharedLib/staticLib)

Critical edge case: A private top-level function with @CName still survives DCE and gets a C-callable bridge — even though the CAdapterGenerator won't include it in the ExportedSymbols struct (it only collects isEffectivelyPublicApi elements). The extern "C" function exists and is callable; it just won't appear in the generated header.

Compiler handling: CAdapterGenerator.kt function functionImplName(); DCE: KonanMangler.kt:25-31 → BinaryInterface.kt:62-64 → DevirtualizationAnalysis.kt:72-81

3.3 @ExportedBridge — Raw C Symbols (No Header)

@ExperimentalNativeApi
@Target(AnnotationTarget.FUNCTION)
@Retention(AnnotationRetention.BINARY)
annotation class ExportedBridge(val bridgeName: String)

Creates a C-callable function with the exact name as a raw LLVM symbol. Key differences from @CName:

Aspect@CName@ExportedBridge
Header entryYes — appears in .h fileNo — must declare manually
Struct memberYes (via shortName)No struct entry at all
Symbol namePrefix may applyExact verbatim name
DCE preventionYes (exported)Yes (EXPLICITLY_EXPORTED)
Bridge codeVia CAdapter pipelineC-to-Kotlin bridge with thread-state switch
Packagekotlin.nativekotlin.native.internal
// Kotlin:
@ExportedBridge("kn_raw_add")
fun rawAdd(a: Int, b: Int): Int = a + b

// C caller — must declare prototype manually:
extern int kn_raw_add(int a, int b);
int result = kn_raw_add(111, 222);

The compiler processes @ExportedBridge in four places:

  1. DCE prevention (DataFlowIR.kt): marks EXPLICITLY_EXPORTED
  2. Symbol naming (BinaryInterface.kt): uses bridgeName as LLVM symbol name, no mangling
  3. Linker retention (RetainAnnotation.kt): prevents linker from stripping
  4. Bridge generation (CodeGenerator.kt): generates C-to-Kotlin bridge with runtime init and thread-state switching
Warning: @ExportedBridge is in kotlin.native.internal — it's an experimental internal API. It's primarily used by the Swift Export pipeline. Use with caution in production code.

3.4 Prefix Control

The prefix is the string prepended to all generated C type names and the symbols accessor. It defaults to the module name (usually the baseName in Gradle) with - and . replaced by _.

// CExport.kt line 22
val prefix = context.config.fullExportedNamePrefix
    .replace("-|\\.".toRegex(), "_")

// KonanConfig.kt line 414
val fullExportedNamePrefix: String
    get() = configuration.get(FULL_EXPORTED_NAME_PREFIX) ?: implicitModuleName

The prefix can be overridden via the compiler flag:

// In build.gradle.kts:
sharedLib {
    freeCompilerArgs += "-Xbinary=fullExportedNamePrefix=myCustomPrefix"
}

// This changes:
//   cexport_demo_KInt        →  myCustomPrefix_KInt
//   cexport_demo_symbols()   →  myCustomPrefix_symbols()

4. Export Visibility Control

Visibility control determines which Kotlin declarations appear in the C header. This is orthogonal to name control.

4.1 Kotlin Visibility Modifiers (Primary Gate)

The C export pipeline checks isEffectivelyPublicApi for every declaration. The compiler's filter predicates (CAdapterGenerator.kt):

// CAdapterGenerator.kt line 53
fun isExportedFunction(descriptor: FunctionDescriptor): Boolean =
    descriptor.isEffectivelyPublicApi
        && descriptor.kind.isReal
        && !descriptor.isExpect
        && !descriptor.isSuspend
        && descriptor.contextReceiverParametersCount == 0
        && descriptor.typeParameters.isEmpty()

// CAdapterGenerator.kt line 62
fun isExportedClass(descriptor: ClassDescriptor): Boolean =
    descriptor.isEffectivelyPublicApi
        && !descriptor.isAnnotationClass
        && !descriptor.isExpect
        && descriptor.typeParameters.isEmpty()
        && !descriptor.isValue
Kotlin visibilityExported to C?Notes
public✅ YesDefault for top-level and class members
internal❌ NoFiltered out by isEffectivelyPublicApi
private❌ NoFiltered out
protected❌ NoNot representable in C
public class, internal member❌ Member hiddenClass is exported but member is filtered
internal class❌ Entire class hiddenAll members gone
In the demo: VisibilityDemo.kt has publicTopLevel() (exported), internalTopLevel() (not exported), privateTopLevel() (not exported), and a PublicClass with mixed-visibility members.

4.2 Gradle export() — klib Dependency Re-Export

For sharedLib, staticLib, and framework binaries, the export() method re-exports a klib dependency's public API into the generated C header:

// app/build.gradle.kts
kotlin {
    ohosArm64 {
        binaries {
            sharedLib {
                export(project(":lib"))          // project dependency
                export("com.example:lib:1.0")    // published klib
            }
        }
    }
}

Without export(): Only the app module's own public API appears in the header. The lib's code is linked into the binary but its symbols are not in the ExportedSymbols struct.

With export(): The lib's public API is added to the header alongside the app's. C code can call both via the same struct:

// App module's own API:
lib->kotlin.root.com.example.app.addNumbers(1, 2);

// Re-exported lib module's API (because of export(project(":lib"))):
lib->kotlin.root.com.example.lib.libAdd(1, 2);

The Gradle export() translates to the compiler flag -Xexport-library=<path>. The compiler collects exported dependencies in FeaturedLibraries.kt:

// FeaturedLibraries.kt line 18
fun ModuleDescriptor.getExportedDependencies(konanConfig: KonanConfig) =
    getDescriptorsFromLibraries(
        (konanConfig.resolve.exportedLibraries + konanConfig.resolve.includedLibraries).toSet()
    )

transitiveExport controls whether transitive dependencies are also re-exported:

sharedLib {
    transitiveExport = true  // also export transitive deps
    export(project(":lib"))
}

4.3 moduleIncludeOnly — Whitelist Filtering

A secondary filter that restricts which modules have their symbols included in the C header:

// In build.gradle.kts:
sharedLib {
    freeCompilerArgs += "-Xbinary=moduleIncludeOnly=lib"
}

// Result: ONLY the "lib" module's API appears in the header.
// The app module's own API is EXCLUDED.

Implementation in CAdapterGenerator.shouldIncludeModule() (line 548):

  • If moduleIncludeOnly is empty → all modules included (default)
  • If set → only modules whose library name contains one of the configured strings (case-insensitive)
  • The main module (without a library) is excluded when this filter is active

4.4 cInterfaceMode — Toggle Header Generation

sharedLib {
    freeCompilerArgs += "-Xbinary=cInterfaceMode=none"
}
ModeEffect
v1 (default)Generate full ExportedSymbols struct header
noneSkip C header generation entirely (binary still produced)

Use none when you only need the binary and will provide your own C API layer.

5. Anatomy of the Generated C Header

For a library with baseName = "cexport_demo", the compiler generates libcexport_demo_api.h:

// ① Header guard
#ifndef KONAN_CEXPORT_DEMO_H
#define KONAN_CEXPORT_DEMO_H
#ifdef __cplusplus
extern "C" {
#endif

// ② Primitive type mappings
typedef int                cexport_demo_KInt;
typedef long long          cexport_demo_KLong;
typedef double             cexport_demo_KDouble;
typedef void*              cexport_demo_KNativePtr;

// ③ Reference types (opaque pointers to Kotlin objects)
typedef struct { cexport_demo_KNativePtr pinned; } cexport_demo_kref_com_example_app_Animal;
typedef struct { cexport_demo_KNativePtr pinned; } cexport_demo_kref_com_example_app_Point;

// ④ The ExportedSymbols struct
typedef struct {
  // ④a: Service functions
  void (*DisposeStablePointer)(cexport_demo_KNativePtr ptr);
  void (*DisposeString)(const char* string);
  cexport_demo_KBoolean (*IsInstance)(cexport_demo_KNativePtr ref, const cexport_demo_KType* type);

  // ④b: Nullable value creators/accessors
  cexport_demo_kref_kotlin_Int (*createNullableInt)(cexport_demo_KInt);
  cexport_demo_KInt (*getNonNullValueOfInt)(cexport_demo_kref_kotlin_Int);

  // ④c: User functions — hierarchical package structure
  struct {
    struct {
      struct {
        struct {
          struct {
            // Top-level functions
            cexport_demo_KInt (*addNumbers)(cexport_demo_KInt, cexport_demo_KInt);
            // Classes
            struct {
              cexport_demo_KType* (*_type)(void);
              cexport_demo_kref_..._Animal (*Animal)(const char* name, cexport_demo_KInt age);
              const char* (*speak)(cexport_demo_kref_..._Animal thiz);
            } Animal;
          } app;
        } example;
      } com;
    } root;
  } kotlin;
} cexport_demo_ExportedSymbols;

// ⑤ Global accessor function
extern cexport_demo_ExportedSymbols* cexport_demo_symbols(void);

// ⑥ @CName(externName) standalone functions
RUNTIME_EXPORT extern "C" cexport_demo_KInt kn_subtract(cexport_demo_KInt, cexport_demo_KInt);

#ifdef __cplusplus
}
#endif
#endif

8. What Is NEVER Exported to C

The following are filtered out by the compiler regardless of visibility:

Language featureWhy filteredCompiler check
suspend functionsContinuation-based, not representable as C call!descriptor.isSuspend
Generic functions (type params)Type parameters not representable in Cdescriptor.typeParameters.isEmpty()
Functions with context receiversContext parameters not representable in CcontextReceiverParametersCount == 0
expect declarationsNo body to generate bridges for!descriptor.isExpect
Annotation classesNo meaningful C representation!descriptor.isAnnotationClass
value class / inline classUnwrapped to underlying type; class itself not exported!descriptor.isValue
Extension functionsExported as regular functions with receiver as first paramActually exported ✅
value class nuance: The class itself is not exported as a struct, but functions that take/return a value class are exported — the value class is unwrapped to its underlying type. E.g., fun lookupUser(uid: UserId) where UserId(val id: Int) becomes KInt lookupUser(KInt uid) in C.
